# お酒コレクションアプリ「sake-collection」要件定義書

作成日: 2026-11-08（日）。作成: Muse（ユーザーの決定を集約）。
状態: 確定（改訂版）。2026-11-08 に壁打ちで確定した後、6者レビュー（Claude／Grok／Argon／Perplexity／ChatGPT／Muse）を受けて改訂。レビューの統合と仕分けは sake-collection-requirements-review-summary.md に残す。
リポジトリ: tahosook/sake-collection（GitHub、2026-11-08 作成）。Antigravity プロジェクト名も sake-collection。

## 1. 目的

手持ちのお酒が何本あって、それぞれ何なのかが、開けばすぐ分かるアプリ。

主目的は「どんなお酒を持っているかを知ること」。何を飲むか決める支援は主体ではない（決めるのは自分でできる）。

## 2. 利用者・利用環境

- 利用者はユーザー本人だけ。共有や他人の評価はなし。
- 主な利用端末はスマートフォン（自宅でコレクションを眺める・買ってきた瓶を登録する）。
- 公開は本人のみがログインできる形（Cloudflare Pages＋Access、認証は Google ログイン・許可は本人のみ）。プレビュー用途の公開も含め、最初から Access で保護する。

## 3. 対象範囲

### 対象
- 酒全般。種類は日本酒／ワイン／ウイスキー／ジン／焼酎／ビール／ブランデー／シェリー／ウォッカ／その他（ユーザーの実際の所持範囲。種類リストは固定とし、足りないものは「その他」とする）。
- 在庫は1本単位。1本＝1レコードとして管理し、1レコードの中での数量や残量（ml・%）の増減管理はしない。
- 状態は未開封／開封済み／飲み切り／手放した の4つ。

### 対象外
- 「今夜のおすすめ」のような決定支援、ペアリング相談、買い足し相談（必要になったら後付け）。
- 店で飲んだものの記録。
- 買い物の管理（購入先の比較、支出集計など）。ただし購入日・購入場所・購入価格の記録自体は対象（§4・§5）。
- 残量の管理。

## 4. 機能要件

開発はステップ単位に分ける。各ステップの詳細と受入条件は設計フェーズで決める。

### 画面とデータの関係（基本定義）
- 普段の一覧に載るのは「いま家にある酒」（未開封・開封済み）。
- 飲み切った瓶は一覧から外れ、「飲んだ記録」として時系列（飲み切り日順）に残る。
- 手放した瓶は一覧から外れ、飲んだ記録とは分けて残る（贈答・譲渡・処分。誰に渡したかなどはメモに書く）。
- 検索は、一覧と飲んだ記録の両方に及ぶ。

### ステップ1：コレクションの把握（最小版）
- 一覧：写真グリッドで全体を眺められる。種類と状態での絞り込み、名前での検索。検索の対象は名前だけでなく、蔵元・蒸留所・産地などの主要な属性も含む。
- 一覧は同じ銘柄をまとめて表示し、何本あるかが分かる。まとめの定義は次のとおり（設計委任ではなく要件で確定）：名前＋種類＋容量が一致するものを同じ銘柄とする。年（ヴィンテージ）が異なるものは別の銘柄として扱う。グループは表示のたびの計算とし、データ自体は1本単位のままにする。
- まとめ表示の細部：グループの並び位置は、グループ内でもっとも優先な状態（開封済み＞未開封）と、もっとも新しい購入日を基準にする。絞り込みは1本単位に適用し、表示される本数は絞り込み後の数とする。本数に飲み切り・手放したは含めない。まとめた表示の中でも、1本ずつ開いて扱えること。
- 一覧の並び：開封済みを上に寄せ、その中で種類ごと（種類の順序は §3 の記載順で固定）→買った順（購入日の新しい順）。購入日が未入力の場合は登録日で代用する。
- 詳細：1本の写真と属性、解説、購入情報が見やすいこと。開封してからの日数は、状態が開封済みで開封日が入っている場合のみ、詳細の開封日の欄に目立たない補助表示として出す（一覧のカードには出さない。開封日が空欄なら出さない）。
- ステップ1には、後続ステップの代わりに最低限の投入手段も含める：最小の手入力登録（名前・種類・状態・購入情報。写真なしでも可）と、状態の変更。
- ステップ1にはバックアップ（データの書き出し・読み込み）を含める。同期（ステップ4）が入るまでの間も、端末のデータ消失に備えるため。
- データの形は最初から同期を見据える：1本ごとに端末をまたいで一意な ID、更新日時、削除フラグを持つ。
- 受入確認にはサンプルデータ（全状態・複数種類・同一銘柄の複数本を含む）を使う。

### ステップ2：登録フロー
- 瓶の写真から登録する。写真は1本につき複数枚を登録できる（ラベル正面・裏ラベル・箱など）。一覧のグリッドには代表の1枚を使い、詳細では全枚見られる。代表写真は指定でき、未指定なら最初の1枚とする。複数枚あることで、Gemini 相談でもネットの商品情報と照合しやすくなる。
- 写真はクライアント側でリサイズ・圧縮し、EXIF（位置情報など）は除去する。端末内では IndexedDB に保持する（localStorage の容量では保持しない）。
- Gemini 相談（プロンプトをコピーして結果 JSON を取り込む、Smart Closet と同じ方式）で、ラベルから属性を抽出する。登録の操作は「写真を選ぶ→相談用プロンプトをコピー→Gemini の結果を取り込む→保存」の流れを目安に、少なく保つ。
- 取り込みの前に内容を確認・修正できること。取り込み時には検証を行い、壊れた JSON・未知の種類・必須項目の欠落は弾くか警告する。登録した内容は後から編集・削除できる（属性・解説・購入情報・写真の追加と差し替えを含む）。誤登録は削除できる。
- ユーザーが編集した項目は、再取り込みで上書きしない（確定した情報を AI の推定で潰さない）。
- 取り込み時に、既存の同じ銘柄があれば知らせる（重複登録の防止）。2本目以降の登録では、既存の銘柄を指定して属性や解説を流用できる。同内容で複数本をまとめて登録することもできる。
- 登録時の状態の既定は未開封。すでに開封済みの瓶も登録でき、その場合の開封日は空欄でもよい。
- 同じ相談で「解説」文も生成する。解説は4部構成（①ひとことで ②味わい ③背景 ④飲み方、目安300〜500字）。構成そのものは種類によらず共通とし、各部の中身の軸は種類ごとに寄せる（②の軸：日本酒なら香り・甘辛、ウイスキーならピート・樽香、ジンならボタニカル、シェリーならタイプ自体が味を決める等。④：日本酒なら温度帯、ウイスキーならストレート／ロック／ハイボール、ジンならカクテル、焼酎なら割り方、など）。軸の詳細は設計で決める。正確さの原則：ネット情報で裏が取れたことだけを書く。分からない項目は推測で埋めず「不明」と明記する。文字数は目安であり、不明が多い場合は正確さを優先して短くなってよい。文体：事実ベースで淡々と書き、宣伝文句のような誇張はしない。解説の出典（参照したページの URL）を一緒に保持し、詳細で確認できるようにする。
- 同じ相談で「相場目安」も推定する（ネットの販売情報から）。条件：通貨は日本円。容量が異なる商品の相場は混ぜない。同じ商品と確認できない場合は無理に推定せず空欄にする。相場目安の取得日は、その相談を実行した日とし、再推定は手動で行い結果で上書きする（履歴は残さない）。相場目安は登録時の参考情報であり、買い物判断の機能は提供しない。
- Gemini に写真を送ることについて、背景の写り込みへの注意を登録の流れの中で示す。

### ステップ3：状態と記録
- 開封・飲み切り・手放した の記録を付ける。
- 状態と日付の関係：未開封のとき、開封日・飲み切り日・手放した日は空欄。状態を変えたら、対応する日付（開封日・飲み切り日・手放した日）はその日の日付で自動設定される。日付は後から手修正でき、空欄に戻すこともできる。状態の変更は取り消せる（誤操作に気付いたら前の状態に戻せる）。
- 感想はメモで残す。メモは1本に1つ（書き直して上書きする形）。星や点数などの評価は付けない。
- 「また買いたい」の印を、付けたいときだけ任意で付けられる。印は飲んだ記録と詳細に表示され、飲んだ記録では印で絞り込みもできる（買い物の場面で「前に飲んで、また買いたいと思った酒か」に答えるためのもの）。

### ステップ4：同期と公開
- 端末間同期（GAS＋Google Sheets、Smart Closet の方式を流用）。通常操作は「今すぐ同期」だけの、覚えなくていい形。
- 同期のルール：競合した場合は最終更新日時が新しい方を優先する。削除は論理削除で伝播させる。空・初期状態の端末から同期しても、既存のデータを上書き消去しない。新しい端末では、同期先から全データ（写真を含む）を復元できる。同期の失敗時の再試行と、再実行してもデータが壊れないこと（冪等性）、初回同期時の既存データの扱いは、設計の必須決定事項とする。
- 認可：GAS のエンドポイントは Cloudflare Access とは別の境界として、合言葉による認証で fail-closed にする（Smart Closet と同じ方式）。Sheets と Drive の共有範囲は本人のみとし、共有リンクは使わない。認証情報を公開リポジトリやビルド成果物、画面側のコードに平文で置かない。同期データはアプリが管理するもので、手動編集を前提としない。
- 写真は非公開の Drive フォルダ（本人のアカウントの特定フォルダのみ）に置き、公開リポジトリやビルド成果物には入れない。写真の取得にも認証を必要とする。写真保存の仕組み（端末内保持と Drive 連携の関係）は、ステップ2の設計時点で確定させる。
- Smart Closet のリポジトリ・Drive フォルダ・Sheet・GAS プロジェクト・Cloudflare プロジェクト・Access の許可設定とは完全に分け、別であることを確認のチェックリストにする。

## 5. データ要件（項目）

### 共通項目
- 名前、種類（日本酒／ワイン／ウイスキー／ジン／焼酎／ビール／ブランデー／シェリー／ウォッカ／その他）
- 度数、容量
- 状態（未開封／開封済み／飲み切り／手放した）、開封日、飲み切り日、手放した日
- 感想メモ（1本に1つ。星や点数などの評価は付けない）
- 「また買いたい」の印（任意）
- 解説（Gemini が生成した文章）と、その出典（URL）
- 購入情報：購入日・購入場所・購入価格（いずれも任意）
- 相場目安：Gemini がネット情報から推定した参考価格。推定であることと取得日が分かる形で持ち、購入価格とは混ぜない・上書きしない（Smart Closet で推定色を確定値として保存しなかったのと同じ原則）
- 同期のための情報：ID（UUID）、更新日時、削除フラグ

### 種類ごとの追加項目（最小限）
- 日本酒：蔵元、精米歩合、特定名称（純米大吟醸など）
- ワイン：品種、産地、タイプ（赤／白／泡など）、年（ヴィンテージ）
- ウイスキー：蒸留所、熟成年数
- ジン：蒸留所、主なボタニカル
- 焼酎：原材料、蔵元（蒸留所）
- ビール：スタイル（IPA／スタウトなど）、醸造所
- ブランデー：産地（コニャック／アルマニャックなど）、等級・熟成年数
- シェリー：タイプ（フィノ／オロロソなど）、ボデガ
- ウォッカ：原料、産地
- 詳細は設計フェーズで確定する。増やしすぎないことを原則とする。

## 6. 非機能要件

- ローカルファースト（端末内保存が正、同期は複製）。
- Smart Closet の本番に一切影響を与えない。
- スマホでの操作性を優先（タップ対象は44px以上、写真中心の画面）。

## 7. 開発プロセス

1. **要件定義**（本書）：Muse が作成し、ユーザーが承認する。
2. **設計**：Antigravity の Argon が本書を基に設計する（技術設計は Argon 主導）。設計では、ステップ1の実装に入る前に、ステップ4までの全体のデータ構造（特に写真の保持と Drive 連携、同期の方式）を確定させる。各ステップの受入条件も設計書に含める。Muse がレビュー（意図との一致／過去の決定との衝突／リポジトリ外リスクの3点）。ユーザーが承認する。
3. **開発**：Antigravity の Flash がステップ単位で実装し、ブランチと PR を作る（マージはしない）。PR 本文に設計条件のチェックリストを含める。
4. **テスト**：自動チェック（リポジトリの標準検証コマンド exit 0）、ChatGPT・Grok のレビュー、ユーザーの実機での受入確認。マージ判断はユーザー、実行は Muse。
